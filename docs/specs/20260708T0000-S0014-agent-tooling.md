## 1. Requirement Details

### Background
- 现有 ouro-ops 采用「Tauri(Rust) → Python sidecar → Ansible」三运行时四语言的固定编排架构。复杂度的根源不是功能多，而是把全部运维知识编码成了静态流程：每适配一个新环境（发行版、云厂商、已有节点接管），都要往 playbook 里加条件分支，维护成本随环境多样性线性增长。
- 方向转变：把「环境适配」从代码变成模型的工作，把确定性留给真正危险的操作。产品从「一个桌面 app」收缩为「一个 CLI + 一组 skills」，agent loop 与交互 UI 复用现成 agent harness（Claude Code / Cowork），不再自研。
- **关于「降低长尾成本」的诚实定位**：真正降低环境长尾的是 L3（agent 处理未知）与容器收敛主机差异；L2 里的已知差异（apt/dnf、ufw/firewalld）是把 Ansible 的条件分支**平移**进脚本，不是消除，且 bash 比 Ansible 模块更难保证幂等——因此本 spec 对 L2 强制幂等辅助库与 verify 配对（见 §2.6）。
- 本 spec 定义 **agent 可见的工具面**与**安全强制模型**：如何分层、每层包含什么、以什么契约暴露、危险边界如何在机制层（而非 prompt）落地。

### Scope
- 定义总体架构：Agent Harness / Skills（runbook） / `ouro` CLI（确定性内核） / 目标机器 四层。
- 定义分层依据（危险度 × 已知度）与三级归属：L1 `ouro` CLI、L2 Skill Scripts、L3 只读诊断。
- 定义 **安全强制模型**（§2.2）：受限 SSH principal、`ouro tool run` 唯一写入口、密钥系统级隔离、带外确认令牌、确定性跨机编排器。
- 定义 `pool-spec.yaml` schema（§2.3）、工具契约（§2.4）、部署验收标准（§2.5）、失败处理与回滚（§2.6）。
- 定义第一版暴露方式与其执行隔离前提（§Non-goals + §2.2）。

**v1 支持矩阵（明确 in/out，超出者 CLI 必须拒绝而非 best-effort）：**

| 维度 | v1 支持 | 说明 |
| --- | --- | --- |
| Pool 数量 | 单 pool / spec | 多 pool 用多份 `pool-spec.yaml`；不在单 spec 内表达多 pool |
| 拓扑 | 单 BP + N Relay | BP 唯一；relay 数量不限 |
| 网络 | mainnet / preprod / preview | 由 `spec.network` 声明，含 network_magic + genesis hash |
| Cardano 拓扑模式 | P2P（默认）与 legacy 二选一 | 由 `spec.topology_mode` 声明，验收按模式分支（§2.5） |
| 已有节点接管 | in-scope（takeover） | 迁移原 `ansible/roles/takeover` 能力，见 p2-6 |
| 并发操作 | 单写者，机器级互斥 | 编排器 machine lock 强制（§2.2）；不支持并发写同一机器 |
| Secrets / SSH 凭据 | 本地 secret store | `~/.ouro/credentials`，仅路径/引用进 spec，明文不进模型/JSON |
| 状态漂移 reconcile | 只读 diff（`ouro status --diff-spec`） | v1 只报告漂移，不自动收敛（自动 reconcile 为 Non-goal） |

### Constraints（均为机制约束，非 prompt 约定）
- **密钥系统级隔离**：冷钥 / KES skey / VRF skey 永不经过模型上下文，也永不离开其所在机器。隔离由 OS 权限保证——诊断（L3）用的 SSH principal 对密钥目录**无读权限**、无 sudo、不能 `docker exec` 读取密钥路径；密钥文件属节点用户、`0400`。详见 §2.2。
- **写操作唯一入口**：一切写操作只能经 `ouro tool run <skill>/<script>` 或 L1 命令执行；agent shell 使用**无写权限的受限 SSH key**，远端写能力由 sudoers allowlist 收敛。裸 `ssh sudo …` / `scp` / `docker rm` 因权限不足而失败，而不是靠红线劝阻。
- **带外确认**：破坏性动作（kes push、rollback、register 提交）需 action-bound、单次有效、由人显式带外签发的确认令牌；CLI 的任何 agent 可见输出**不得**包含可复用令牌。
- **强制审计**：`ouro tool run` 为每次 L1/L2 调用建立审计上下文（invocation id + start/finish/crash 事件 + stdout/stderr 捕获），无审计上下文时脚本默认拒绝写操作。审计不依赖脚本自觉。
- **输出脱敏**：所有脚本默认关闭 `xtrace`，JSON / 审计 / 日志只允许记录 hash、路径、counter 数值与 metadata，禁止任何 skey / cold 内容。
- 主机侧要求收敛为「容器运行时 + SSH 可达」，尽量用容器消解发行版差异。
- 遵循 CLAUDE.md 的 risk-aware interaction 与 status integrity：破坏性操作显式、可确认、可回滚；不存在模糊的成功状态。

### Non-goals
- **不自研监控面板**：交给 SPO 圈标配的 Prometheus / Grafana。
- **不做自动 reconcile**：v1 只做只读漂移 diff，不自动把机器收敛到目标状态。
- 部署验收**不包含**「产出第一个区块」：出块取决于 slot leadership 抽签，交由部署后的 epoch 级监控任务（见 §2.5 note），不阻塞验收。
- **MCP server 延后**：第一版不做 MCP。**但暴露面的安全性不依赖 MCP**——它由 §2.2 的受限 SSH principal + `ouro tool run` + sudoers allowlist 保证。若某 harness 无法提供受限 shell，则该环境**不满足生产安全边界**，只能用于非生产（此约束写入 §2.2）。
- 本 spec 不实现代码，只定义工具面与安全模型规格；实现由 Execution Plan 各 item 承接。

## 2. Outline Design

### 2.1 Architecture / modules impacted
四层结构（详见设计稿 §1）：

| 层 | 角色 | 说明 |
| --- | --- | --- |
| Agent Harness | Claude Code / Cowork | agent loop、确认交互、流式日志、会话记录，全部复用，不自研 |
| Skills（runbook 层） | `ouro-skills/` | SKILL.md 只写决策树与红线；`scripts/` 承载全部已知操作逻辑 |
| `ouro` CLI（确定性内核） | Rust 单二进制 | 密钥、签名、配置渲染、审计、审计化脚本执行入口、确定性编排 |
| 目标机器 | BP / Relay | 节点跑容器；两类 SSH principal：受限诊断身份（L3）、经 sudoers allowlist 的执行身份（L1/L2） |

移除项：Ansible、Python sidecar、Tauri/React 整体删除。原 Jinja2 模板迁入 `ouro config render`。

**从 `src-tauri` 抽取的旧依赖 → 新归属（p1-1 不是「剥离 Tauri 依赖」这么简单）：**

| 现有耦合（`src-tauri/src/commands/kes.rs`、`pool.rs`） | 新归属 |
| --- | --- |
| `AppHandle` / `tauri::State` / `app_data_dir` | 独立 CLI config discovery + 本地 staging 目录策略 |
| `DbState`（SQLite repo，机器/任务/审计表） | storage + audit crate（独立于 Tauri），含 legacy DB 迁移 |
| `SidecarState` + `run_playbook`（**KES 生成/推送当前走 ansible-runner 远程执行**） | **新建 SSH runner 层替代 ansible-runner**（这是 p1-1 的主体工作量，非附带项） |
| task 表 / 异步任务模型 | CLI 同步执行 + 审计事件（不搬 Tauri task 模型） |
| GitHub 下载（cardano-cli bundle 等） | CLI 内置 fetch，按 version/platform 缓存（复用现有逻辑） |

### 2.2 安全强制模型（Enforcement）—— 修复评审 P0/P1
安全边界落在机制，不落在 prompt。四条强制：

1. **两类 SSH principal（密钥读隔离，修复 P0#1）**
   - `ouro-diag`（L3 诊断）：普通用户，无 sudo，对 `/opt/cardano/keys/*`、`/opt/cardano/config/keys/*`、bundle/staging 目录**无读权限**，不能 `docker exec` 进节点容器读密钥。L3「自由只读」的自由被系统权限**收窄到非密钥资源**。
   - `ouro-exec`（L1/L2 写）：仅能经 sudoers allowlist 执行 `ouro tool run` 白名单内的命令。
   - 密钥文件属节点用户、`0400`；容器内密钥路径不映射给诊断身份。

2. **`ouro tool run` 唯一写入口（写绕过 + 审计强制，修复 P0#2 / P1-audit）**
   - 所有 L2 脚本只能经 `ouro tool run <skill>/<script> --spec <f>` 启动；CLI 负责：建审计上下文（invocation id、start/finish/crash）、注入只读 token、捕获 stdout/stderr、校验调用者身份。
   - 脚本检测到无审计上下文（被直调）时**默认拒绝写操作**并 exit 10。
   - agent shell 的 SSH key 无远端写权限；即便 agent 尝试 `ssh host sudo …`/`scp`/`docker rm`，因权限收敛而失败。
   - **暴露面前提（写入 Non-goal 的硬约束）**：若 harness 无法提供受限 shell / 无法限制 SSH key 能力，该环境不满足生产安全边界。

3. **带外确认令牌（确认门不可被 agent 绕过，修复 P1-confirm-token）**
   - 令牌由人显式签发：`ouro confirm create --action kes-push --machine bp --ttl 60s`，绑定 `action+machine` 的 hash，单次有效。
   - agent 无签发权限；CLI 拒绝时**不打印**可复用令牌，只提示「需人工签发确认令牌」。
   - 缺有效令牌或令牌 action 不匹配 → 危险命令拒绝执行并非零退出。

4. **确定性跨机编排器（serial/可用性不变式，修复 P1-orchestrator）**
   - 跨机顺序不写进 SKILL.md 决策树，而由 `ouro plan apply`（或 `upgrade/scripts/run.sh`）执行：持久化 phase、**machine lock**、relay quorum、**BP-last**、verify-before-next、失败即停批次（rollback-stop）。
   - 硬不变式：任一时刻保持「BP + 至少一个 relay 在线」；会破坏该不变式的 `upgrade-one` 调用被编排器拒绝（exit 10），不依赖 agent 自觉。
   - SKILL.md 只选择 plan 与参数、表达停止条件与红线，**不含 bash/SSH 原语，也不负责执行循环**（这同时消解了「SKILL 纯编排命令序列」与「SKILL 不含命令序列」的矛盾：SKILL 可列工具名与顺序，不可列命令原语）。

### 2.3 `pool-spec.yaml` Schema（修复 P1-schema，其余 item 的前置）
`pool-spec.yaml` 是用户唯一需提供的声明式目标状态。v1 定义 `pool-spec.schema.json`（版本化，`spec_version` 必填），字段概要：

```yaml
spec_version: 1
pool:
  ticker: OURO
  network: mainnet            # mainnet | preprod | preview
  network_magic: 764824073    # 与 network 必须一致，validate 强校验
  genesis_hashes:             # byron/shelley/alonzo/conway，验收断言比对
    shelley: "1a3be38b..."
  metadata_url: "https://..."
  pledge_lovelace: 100000000000
  margin: 0.02
  cost_lovelace: 340000000
topology_mode: p2p            # p2p | legacy，验收按此分支
node_version: "10.5.4"
machines:
  - id: bp1
    role: bp                  # bp | relay
    ssh: { host: 10.0.0.10, port: 22, user: ouro-exec, key_ref: "creds://bp1" }
  - id: relay1
    role: relay
    public_endpoint: { host: relay1.example.com, port: 3001 }
    ssh: { host: 203.0.113.5, port: 22, user: ouro-exec, key_ref: "creds://relay1" }
sync:
  mode: mithril               # mithril（默认）| genesis
  mithril:
    aggregator_endpoint: "https://aggregator.release-mainnet.api.mithril.network/aggregator"
    genesis_verification_key_ref: "creds://mithril-gvk"
    verify_snapshot_digest: true
```

规则：敏感值只允许 `key_ref` / `creds://` 引用（解析自 `~/.ouro/credentials`，明文不进 spec / 模型 / JSON）；`ouro spec validate` 输出 `spec_version`、resolved non-secret plan、缺失字段列表；**无任何隐式环境变量也能渲染完整 dry-run plan**。

### 2.4 工具契约与 KES 协议
- **输入**：只有 `pool-spec.yaml` + 显式命令行参数（如 `--machine relay1`）；工具业务语义不依赖未声明的环境变量（仅 `OURO_*` 白名单可配置）。
- **输出：单行 JSON**，含 `tool` / `machine` / `status` / `changed` / `checks[]` / `duration_s` / `audit_id`；失败含 `error{code, detail, hint}`。所有 L1/L2 stdout 受 `tool-output.schema.json` 约束，CI 用 validator 校验，禁止出现 secret 字段。
- **L1 命令清单**：`ouro spec validate`（只读）、`ouro config render`（只产出文件）、`ouro config apply --machine`（审计，唯一配置下发路径）、`ouro status [--diff-spec]`（只读 JSON）、`ouro pool overview`（只读：pool 参数 / 质押 / 委托概览，替代原 Delegators 页的点态数据）、`ouro kes generate` / `ouro kes push` / `ouro kes counter status`（见下）、`ouro pool register-tx`（未签名，审计）、`ouro rollback`（确认 + 审计）、`ouro confirm create`、`ouro tool run`、`ouro audit log`（只读）。
- **KES 协议（修复 P0#3 + counter，避免相对现网 cert-only 实现倒退）**：
  - `ouro kes generate`：**KES keypair 在 BP 本地生成**，控制面只取得 KES vkey（或其 hash）；skey 永不出 BP。
  - 离线签发：冷环境只接收 KES vkey + kes period + counter 提示，输出 `node.cert`。
  - `ouro kes push`：**仅安装 opcert（node.cert）**，是轮换路径；VRF 不参与轮换；skey 已在 BP。措辞不再是「推送三件套」。
  - import/push 前校验：cert 类型、issuer、KES vkey 匹配、period 在有效窗口、**counter 单调（== 本地记录且 > 链上/本地已知值）**；不满足则非零退出并禁止 push。`ouro kes counter status` 提供只读对齐视图。
  - JSON / 审计只记录 hash / 路径 / counter 数值 / cert metadata。

### 2.5 部署验收标准（本节为执行标准，修复 P1-network / P1-P2P；扩展设计稿 §6）
`deploy/verify.sh` 输出每条 check 的 `name / pass / severity / exit_class / rollback_safe`；总 exit code 由最高风险项决定（不再「任一 fail 一律 exit 30」，避免 transient 失败误触发回滚）。四范围 + 新增网络身份与拓扑分支：

- **每台机器**：容器运行且启动 10 分钟内重启=0；版本 == `spec.node_version`；tip 与网络 tip 差 <60s 且 slot 推进（网络 tip 取 `spec` 声明的 reference relay）；`:12798/metrics` 200 且含 node 指标；chrony offset <50ms。
- **网络身份（新增）**：本地 genesis hash == `spec.genesis_hashes`；node config network / `RequiresNetworkMagic` 与 `spec.network_magic` 一致；`query tip` 网络参数、Mithril aggregator network 一致——**防止「错网络下看似同步」**。
- **拓扑（按 `spec.topology_mode` 分支，新增）**：
  - P2P：校验 `localRoots`（BP↔自家 relay）、`publicRoots`、`PeerSharing` 配置；relay 被公网 peer 发现；BP 仅 localRoots 连自家 relay。
  - legacy：outbound>0 且 inbound>0；BP peer 列表仅自家 relay。
  - 两模式共有：relay 只暴露预期端口；BP 节点端口自公网**不可达**（防火墙断言）。
- **DB 完整性（新增）**：无 era mismatch / ledger 损坏；Mithril 恢复记录 snapshot digest + 证书链校验通过 + 恢复后 ledger sanity。
- **BP**：forging enabled（KES/VRF/opcert 已加载）；KES 剩余期数 > 阈值（默认 30 期；mainnet 每期 ≈1.5 天、最大 62 期，故 30 期 ≈ 剩 45 天、约半个 key 生命周期）——同时上报剩余天数便于人读。
- **池级（如含注册）**：pool ID 可查；pledge / margin / relay 端点与 spec 匹配，且查询网络与 `spec.network` 一致。

note：验收不含「产出第一个区块」；出块验证交给部署后 epoch 级监控（leadership schedule 可计算 + 应出块窗口未 forge 的告警），属 troubleshooting/observability skill，不阻塞验收。

### 2.6 失败处理与回滚
- **两条硬性性质**：幂等（提供统一 check-then-act 辅助库 `ouro-lib.sh` + 每变更前 detect 规范，让「第二次 changed=false」可达成且可测）；verify 配对（每个变更脚本必有对应 verify，变更后强制执行）。
- **Exit code 分类**：`0` 成功 / `10` 前置条件不满足或无审计上下文（未变更，可重跑）/ `20` 执行失败但安全（未变更，L3 诊断）/ `30` 已部分变更且有可用 backup（先 rollback 再诊断，禁止继续）/ `40` 状态未知（停止一切写操作，呼叫人工）。每条 verify check 按此归类，transient/可等待归 20 而非 30。
- **失败处理阶梯**：脚本内确定性处理 → 结构化失败退出 → agent L3 只读诊断 → 提出修复方案（等人确认）→ 参数化执行（仍走 L1/L2 工具）。
- **双轨回滚语义**：`upgrade/scripts/rollback.sh`（L2，恢复本次批次 backup artifact）与 `ouro rollback --machine --to <backup-id>`（L1，按备份点回滚）职责区分——exit 30 时先调 L2 `rollback.sh`，必要时再 L1 rollback；backup-id ↔ L2 artifact 的映射由 CLI 维护。
- 回滚作为前向变更处理，不改写历史。

### 2.7 退役清单（Decommission inventory）—— 补 p4 退役的物料
新方案下老代码分三类处置。**「先移植 / 转脚本」类必须先达成 parity 才允许删除「直接退役」类；退役不是一个 checkbox，按本清单逐类追踪（见 p4-3~p4-5）。** LOC 为现状量级（React `src/` ~7.7k、src-tauri ~14.9k、sidecar ~0.3k）。

**A. 直接退役（无移植，能力由 harness / Grafana 承接）**

| 组件 | LOC | 替代去向 |
