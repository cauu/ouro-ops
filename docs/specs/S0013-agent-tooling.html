Agent 侧工具的拆分与定义

从「Tauri + Ansible 固定编排」演进为「CLI + Skills」：prompt 只做调度与诊断，一切写操作走确定性工具。本文定义 agent 可见的工具面——如何分层、每层包含什么、以什么契约暴露。

1总体架构

Agent Harness Claude Code / Cowork——agent loop、确认交互、流式日志、会话记录，全部复用，不自研
↓ 加载
Skills（runbook 层） SKILL.md 只写决策树与红线；scripts/ 承载全部已知操作逻辑
↓ 调用
ouro CLI（确定性内核） Rust 单二进制：密钥、签名、配置渲染、审计——危险且已知的操作只在这里发生
↓ SSH（唯一传输层，无框架）
目标机器 BP / Relay，节点跑容器，主机侧要求收敛为「容器运行时 + SSH 可达」

Ansible、Python sidecar、Tauri/React 整体移除。原 Jinja2 模板迁入 ouro config render；原 playbook 逻辑按下述三层重新归位。

2拆分依据：危险度 × 已知度

每个操作按两个维度归类：做错的代价（危险度）和能否预先写成代码（已知度）。这决定它属于哪一层、以什么形式暴露给 agent。

L1  ouro CLI

危险且已知 · Rust · 确认门控 + 审计

密钥生成与推送、注册交易、配置渲染、回滚触发。错一次代价极高，因此用最可测的形式实现。

冷钥与签名永不经过模型上下文；破坏性动作 CLI 层强制确认，与 agent 是否可靠无关。

L2  Skill Scripts

普通且已知 · Bash · 幂等 + JSON 契约

装依赖、系统准备、配置下发、重启、逐台升级。已知的环境差异（apt/dnf、ufw/firewalld）在脚本内部用确定性代码探测处理。

每个变更脚本配对 verify；失败以结构化错误退出，绝不「尽力而为」。

L3  只读诊断

未知情况 · 自由命令 · 严格只读

读日志、查 systemd 状态、拉 metrics、看磁盘内存。这是 agent 自适应能力的用武之地：看懂现场，而不是即兴改机器。

诊断自由，写入禁止——发现问题后仍须通过 L1/L2 参数化执行修复。

读写分界是整个设计的一条线：read = 自由，write = 工具。agent 的价值是缩短「失败 → 诊断」的路径，而不是获得即兴写生产机器的权力。

3L1 工具清单：ouro CLI

命令作用门控
ouro spec validate静态校验 pool-spec.yaml（角色、端点、版本合法性）只读
ouro config render --machine <m>由 spec 确定性生成 node config / topology（替代 Jinja2 模板）只产出文件
ouro status --machine <m>结构化运行状态：tip、slot lag、peers、KES 剩余期数（JSON）只读
ouro kes generate生成新 KES 密钥对 + opcert（cold counter 在离线机递增）确认 + 审计
ouro kes push --machine bp推送热钥三件套到 BP 并滚动重启确认 + 审计
ouro pool register-tx构造注册 / 更新交易（未签名，签名永远离线）审计
ouro rollback --machine <m> --to <backup-id>回滚到指定备份点确认 + 审计
ouro audit log查询 append-only 审计日志（每次 L1/L2 调用自动落库，无论谁调的）只读

复用现有 src-tauri/src/commands/ 中 kes.rs、pool.rs 的 Rust 逻辑，剥离 Tauri 依赖抽为独立二进制。

4L2 工具清单：Skill Scripts

ouro-skills/
├── deploy/
│   ├── SKILL.md            # 决策树 + 红线，约 1 页
│   └── scripts/
│       ├── preflight.sh    # 只读：硬件/端口/发行版/连通性 → JSON 报告
│       ├── provision.sh    # 幂等：容器运行时、用户、chrony、防火墙
│       ├── sync.sh         # Mithril 快照恢复（默认）或 genesis 同步
│       ├── start.sh        # 拉起节点容器
│       └── verify.sh       # tip 推进、peer 连接、metrics 可达
├── upgrade/
│   └── scripts/            # preflight / backup / upgrade-one / verify / rollback
├── runtime/
│   └── scripts/            # topology-apply / restart / verify
├── observability/
│   └── scripts/            # install-gateway / verify / rollback
├── kes-rotation/
│   └── SKILL.md            # 无脚本：纯粹编排 ouro kes 命令序列
└── troubleshooting/
    └── SKILL.md            # 唯一以 prompt 为主的 skill，限定 L3 只读

判断标准：SKILL.md 里一旦出现具体命令序列，就该下沉为脚本。脚本可在 CI 里对容器矩阵（Ubuntu / Debian / Rocky）做集成测试——prompt 测不了，脚本测得了，这是确定性的来源。

5工具契约

agent 与工具之间的接口必须让模型「只解析结构，不猜测文本」。所有 L1/L2 工具遵守同一契约：

输入

参数来源只有两个：pool-spec.yaml（声明式目标状态，用户唯一需要提供的信息）+ 显式命令行参数（如 --machine relay1）。工具不依赖环境变量或隐式状态。

输出：单行 JSON

// 成功
{"tool":"upgrade-one","machine":"relay1","status":"ok","changed":true,
 "checks":[{"name":"tip_within_60s","pass":true}],"duration_s":184}

// 失败（结构化，含下一步提示）
{"tool":"upgrade-one","machine":"relay1","status":"failed_needs_rollback",
 "error":{"code":"NODE_NOT_SYNCING","detail":"tip lag 3402s after restart",
          "hint":"run rollback.sh, then diagnose via journalctl"}}

Exit code 分类

Code语义机器状态agent 必须做的事
0成功已变更且 verify 通过继续下一步
10前置条件不满足未变更修复前置条件后重跑（幂等）
20执行失败（安全）未变更L3 只读诊断 → 报告
30执行失败（已部分变更）不一致先 rollback，再诊断，禁止继续
40状态未知无法判定立即停止一切写操作，呼叫人工

两条硬性性质

幂等：任何脚本重跑不产生副作用，这让「修复后重试」成为安全的默认动作。verify 配对：每个变更脚本必须有对应 verify，变更后强制执行——不存在模糊的成功状态（对应设计原则 status integrity）。

6部署验收标准

「部署成功」不是一段描述，而是 deploy/verify.sh 的断言清单：全部 pass 才算完成，任一 fail 即验收不通过（exit 30，走回滚阶梯）。每条断言输出到 JSON 的 checks[]，agent 与人看到的是同一份结果。

范围断言判定方式
每台机器 节点容器运行且稳定运行中，且启动后 10 分钟内重启次数 = 0
版本与 spec 一致ouro status 上报版本 == spec.node_version
同步完成本机 tip 与网络 tip 差 < 60s，且 slot 持续推进
metrics 可达:12798/metrics 返回 200 且含 node 指标
时钟同步chrony offset < 50ms（slot 计算依赖时钟）
Relay 公网可达从操作机对 public_endpoint TCP 拨测成功
双向 peer 建立outbound > 0 且 inbound > 0（inbound 证明公网真实可达）
与 BP 互连peer 列表包含 BP 内网地址
BP 出块已使能日志/指标显示 forging enabled，KES/VRF/opcert 已加载
KES 有效期充足剩余期数 > 阈值（默认 30 期）
拓扑隔离仅连接自家 relay；节点端口自公网不可达（防火墙断言）
池级（如含注册） 链上状态与 spec 一致pool ID 可查，pledge / margin / relay 端点与 spec 匹配

验收不包含「产出第一个区块」——这取决于 slot leadership 抽签，可能在数天之后。出块验证交给部署后的监控：scheduled task 每个 epoch 检查 leadership 排期与 forge 指标，属于 troubleshooting/monitoring skill 的职责，不阻塞部署验收。

7SKILL.md 的角色：调度，不是操作

以最复杂的 upgrade 为例，SKILL.md 的全部内容就是这样一棵决策树：

1. ouro spec validate → 每台机器跑 preflight.sh，任一 exit 10 → 修复后重跑
2. 逐台执行，relay 在前、BP 最后，每台：
     backup.sh → upgrade-one.sh → verify.sh
   verify 通过才允许下一台（原 Ansible serial:1 语义，一句话表达）
3. 任一台 exit 30 → rollback.sh → 停止整个批次 → L3 诊断 → 报告
4. 红线：
   - BP 与任一 relay 不得同时离线
   - 任何 exit 40 → 停止全部写操作，呼叫人工
   - 写操作仅限本 skill 列出的工具，禁止即兴 SSH 写命令

8失败处理阶梯

环境长尾（未知发行版、诡异报错）不靠预写分支覆盖，靠这个阶梯：

脚本内确定性处理已知差异（包管理器、防火墙）在脚本内探测解决，不消耗模型
结构化失败退出遇到未预见情况，带 error.code / detail / hint 退出，不「尽力而为」
agent 只读诊断L3 自由读取日志、状态、指标，形成对现场的判断
提出修复方案向人说明原因与拟采取的动作，等待确认
参数化执行确认后仍通过 L1/L2 工具执行修复，然后 verify、重试原步骤

9Agent 行为红线（写进每个 SKILL.md）

① 写操作只能调用列出的工具，禁止手搓 SSH 写命令。
② L3 诊断禁止 sudo 写入，只读命令自由。
③ 密钥材料（cold/KES/VRF）不得读入模型上下文，一律经 ouro CLI 流转。
④ exit 30 必须先回滚；exit 40 停止一切写操作并升级到人工。
⑤ 每次变更后必须 verify，verify 失败视同操作失败。

红线的最终保障不在 prompt：确认门、审计、密钥隔离都在 CLI 层强制执行。即使 agent 行为异常，危险操作也过不去。

10暴露方式：CLI + Bash 优先，MCP 可选

第一版不做 MCP server：agent harness 本身就有 bash 工具，CLI 在 PATH、脚本在 skill 目录即可被发现和调用，且 JSON 契约已保证输出可解析。当出现「非 bash 环境的 agent 也要接入」或「需要更细粒度权限声明」的需求时，再用薄薄一层 MCP 包装 ouro CLI，工具语义不变。
